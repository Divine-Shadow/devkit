# Durable native homes and reset admission

Decision owner: Source1, under the original 1 November purge source commission.
Phase: source implementation and qualification under the resumed original-purge
commission. Existing CI-controlled publication and owner-routed rollout are
authorized; this source record does not itself execute a live migration or reset.

## problem

Native execution reset currently owns paths containing usable application data.
Selecting persistent host storage outside those paths also requires protecting
legacy data that may exist before migration. A planning-time absence check loses
that protection if data appears later or is moved into numbered quarantine paths.
Whole-prefix disposal also spans repositories beyond its primary repo argument.

## options

1. Keep copying history into predecessor archives and import it after reset.
   This retains a mandatory recovery graph and does not keep the same usable
   database, companion files, history and goals outside disposable computation.
2. Bind source-selected durable storage into the existing sandbox home, exclude
   that host root independently, and carry precise legacy-data obligations
   through the existing reset transaction. Refuse unmapped old quarantine.
3. Accept quarantine names as disposal authority and check active paths once.
   Numeric staging can hide protected data and a fresh retry can delete it.

## selection_rationale

Choose option 2. The real nested bubblewrap home bind leaves an empty worktree
mountpoint scaffold. Recognize only that exact owned, canonical real directory
with mode0700/0755 and no entries, inspected through a held descriptor. Never
apply that allowance to execution-state homes. This avoids moving application
data while keeping the established logical home unchanged. Correctness preserves the actual data boundary and all real
containment rules. Disposable fixtures can verify same-object SQLite/history
survival, late data, staging, recovery and rollback. Safety keeps uncertain old
payload intact rather than inferring ownership from its name. Source-derived
paths and the existing transaction mapping remain the authority; no new registry,
runtime identity, credential or mandatory ordinary-entry institution is added.
Speed does not justify deleting uncertain data or weakening a mount guard.

## safety_checks

The opaque plan owns exact legacy state/home and lane-home obligations. The
whole-prefix first lane checks every repository. Staging and irreversible
cleanup recheck active and mapped quarantine locations without following payload
symlinks. Fixed path components are literal even when their names contain glob
metacharacters; only the explicitly typed whole-lane repository component varies.
Fresh staging cannot reclaim opaque old quarantine without its actual
transaction mapping. Structural recovery continues to permit safe restoration;
deletion admission separately checks data. The writable home-bind exception
matches only the selected persistent home and its existing sandbox destination.
GUI-required lifecycle planning derives the same isolated workspace from source
paths used by actual launch. Process custody uses each declared host/sandbox
home-worktree pair and still proves both objects through the process root with
os.SameFile. Historical relative-layout aliases retain physical verification;
matching a home alone never grants process custody.

The typed worktree-home allowance follows the existing source/quarantine mapping
and is rechecked before destruction. Hidden or late data, unsafe ownership/mode,
redirection and state-root homes still refuse; rollback preserves late data.
Actual repeated CLI entry writes SQLite through logical HOME and reads the same
physical persistent storage, while its worktree scaffold stays empty.

Whole-reset process/history observation uses source geometry and the same strict
immutable GUI selection without constructing a runnable plan or adopting opaque
Git payload awaiting disposal. Ordinary launch retains all Git bind/backlink
guards. Active-sibling scans still precede history and reset application, and
foreign Git data must remain unchanged after source reconstruction.

Managed SSH consumes physical retained storage from the
admitted source state root and exact matching dev-all slot. Canonical Product
worktree, immutable GUI class/host, logical home, actual restrictions and SSH
policy remain required; legacy/sibling/foreign storage still refuses. This avoids
assuming that canonical worktrees and independently declared state share a root.

History callers request an additional workspace alias only when the actual
source plan projects through /workspaces/dev. Other native containers retain
their explicit physical/logical homes and all reference checks; an undeclared
workspace alias remains foreign and refuses without changing protected data.

Run affected Go packages and normal integrated CI, independent source review,
paired caller/WSL qualification, then actual ordinary receiving when allowed.
Source fixtures alone do not establish migration or usable GUI lifecycle results.

## rollback_plan

Before selection, retain this isolated unpublished candidate and the published
baseline; do not modify deployed runtime or existing data. Reject this candidate
if containment or data-retention fixtures fail. After any future authorized
migration, never revert to an old binary's home mapping or copy/merge data to
force rollback. The environment owner must retain the actual durable location
and select a compatible published composition through its normal route.

## decision_scope

Devkit path selection, preparation guards, exact native home bind, reset
transaction data admission, bounded migration, consumer projection and physical
custody joins, and disposable fixtures. Paired WSL composition, full CI,
publication and actual receiving remain unfinished.
Main retains Product source authorship; Runtime/Environment own live effects.
